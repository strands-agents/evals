# Browser tests for `strands-evals ui`

The page served by `strands-evals ui` is a single HTML file at
`src/strands_evals/cli/assets/ui.html`. Its discovery, pairing and write logic lives in Python and
is covered by `tests/strands_evals/cli/test_ui.py`; what is left in the page is rendering, and
rendering is where it can be *confidently wrong* — claiming a trajectory is absent when it is
merely an unexpected shape, or counting a failure to judge as a skipped row. These suites run the
real file in jsdom and assert on what it puts on screen.

Not wired into CI, because CI has no Node toolchain. Run them by hand when the asset changes:

```bash
cd tests/ui
npm install          # jsdom only
npm test             # every suite
node standalone.mjs  # or one at a time
```

`server.mjs` starts the real `_ui_server` as a subprocess and forwards the page's `fetch` to it, so
it exercises the HTTP contract rather than a mock of it. It needs a Python that can import
`strands_evals`; override with `PYTHON=/path/to/venv/bin/python npm test`. Point the suites at a
different build of the page with `UI_HTML=path/to/ui.html`.

| Suite | Covers |
| --- | --- |
| `standalone.mjs` | the file opened with no server: bundled sample, folder picker, download-save, add/delete case, evaluator config editing, trajectories that are dicts or a `Session` |
| `fileorigin.mjs` | the file opened from disk over `file://`, which `standalone.mjs` does not cover — it boots at an http URL, so it never reaches the APIs an opaque origin restricts. `history.replaceState` refuses a URL it cannot verify against one, and that rejection used to abort rendering entirely |
| `extras.mjs` | the row cap, deep links — including one saved as `tab=optimization`, from when that section was a single view, which lands on the result it was looking at and is rewritten to the name the page now uses — reports missing their optional arrays, a mismatched experiment↔report pair, runs with only one half. Also the run list's two jump cells: the experiment and report columns open their own tab, but only where there is something behind them — a "not run yet" cell does what its row does rather than opening an empty Report — and a jump within the run already open must not re-read it from disk, since the unsaved-changes prompt only fires when the run *changes*. And the ink the property names are set in: jsdom does not substitute custom properties, so a computed `color` comes back as the literal `var(--inkN)` the stylesheet asked for, which is what field labels, column headers and detail keys are checked against — plus the muted ink itself against 4.5:1, so promoting the labels cannot just move the problem down to the hints. Then the metadata editor, where the contract is what reaches the file: a value is `Any`, so `4` has to land as a number and `hello world` as a string, a renamed key has to replace rather than join the old one, emptying the last key has to delete the whole dict, and a blank row the `+ key` button just offered is *not* an edit — mutating the case there would both mark it dirty for nothing and write a `""` key if saved before being filled in. The glyph strip and draft badge are read from the same objects, so an empty `{}` earning a glyph would be the same bug seen from the list. And the review pass, which is the only place in the page a bare keystroke changes the document: it moves the selection to the case being decided, `a` and `d` are off while a field has focus, `drop` is written out by Save like Delete rather than touching the file, and the pass closing is announced *after* the re-render that would otherwise clear the message. Last, the link out to the run explorer, which is a link and not a tab: shown only when `/api/config` reports a runs directory, pointing at `/explorer/` with the token url-encoded in the query and the route in the hash (the order the explorer reads them in), opening in its own tab, and sitting beside the candidate table it zooms into rather than in the tab row — it carries no `data-view`, which the tab handler would otherwise pass to `show(undefined)` and blank the view on the way out |
| `optimization.mjs` | the Optimization section, over `fixtures/optimizer-run`. The section itself first: it does not exist at all for a folder holding no run directory, so a folder of plain experiments reads as it did before there was an optimizer, and its three tabs — **Runs**, **Setup**, **Results** — are this section's rather than Evals' three renamed. Runs lists the run directories the way Evals lists experiment/report pairs, with the champion, the search, the stop reason and a marked row saying which run the other two tabs are showing, so the list and the result cannot disagree. Setup is the record as written and is read-only: it holds nothing to type into, because nothing in the page writes a `run.json`. It is also where the two spellings of that record meet — the fixture names the fields the way `optimization/record/events.py` documents them, while the runs under `examples/optimization/runs` put the goal metrics in the `objective` roles of `metrics`, the tunable blocks inside `search.blocks`, the repeats in `runs_per_candidate`, the score model and pick rule under `name`, and say Pareto only in the objective string — so each of those rows is asserted against a config in the written shape, since a field read under one name is a row that is simply absent for every real run. It is also where the **method** lives, because no number under Results can be read without it: the search only saw train, the pick happened once on validation, and the experiment was never run itself. Then the **result**, which is what the page opens on: the champion against the baseline on the held-out split, where every figure has a wrong neighbour in the log it could have come from instead (the training best, the validation objective, a mean over the cases the search chose on). The verdict is the *interval*, not the gap, so there are logs differing only in that — one clearing zero, one straddling it, one negative, one with no interval at all, and one whose interval is narrow enough that rounding to two decimals would flip the verdict. A `picked`-only run is labelled validation rather than held out, and reads `measured` where a test report says `means`. Then the **winner**: its lineage back to the baseline, only the settings that actually differ, a multi-line prompt diffed as a block, and what the copy button really hands over (the whole configuration, inherited settings included) — with the fallback saying so when the clipboard is unreachable. Then the **candidates**, which the tab treats as what `RunDirectory.reports()` says they are — an evaluation run of one configuration. So a row opens onto the diff against the *baseline* (not the parent, which `changed_keys` already is), its measured metrics and every trial grouped by split in run order; the search reaches into the configuration values, so a phrase from a tuned prompt finds the candidate that says it; and "open as report" builds an `EvaluationReport` from the trials and hands it to Evals' Report panel, where a failed trial still counts as a failing row, a case input the trial never recorded is named as absent rather than printed as `undefined`, and the `{hash, format}` transcript pointer is left out rather than dressed up as a recorded conversation. That panel is *borrowed*, not reassigned: the jump says whose report is in it and gives the one click back, because overwriting the report Evals had loaded while its Runs tab went on highlighting that run was the page contradicting itself. A trial row opens further, onto the one thing on this tab that is not derived from the log: how it ended, what each evaluator made of it, what it cost, the answer it gave, and the **conversation** behind it — a file in the run directory that the log only points at by hash. So the transcript is read off the *document* rather than the `format` the pointer claims, in both shapes: a `Session`, counted in spans and labelled by span kind, since printing a tool's result as a message would have the model saying it out loud; and a list of Strands messages, counted in messages, with usage on the one that recorded any and reasoning shown but set apart from what the model actually said. Tool output arrives as a JSON string far more often than as a structure, so a lone `{"output": "..."}` is laid out as the tool's text rather than as the envelope it came in. And the four ways there can be nothing to show are four different facts about a run, so they read as four: a trial that recorded no transcript, a pointer whose file the opened folder did not hold (named, with the picker's depth limit as the likely reason), a pointer the server answers 404 for — "not in the run directory", which only served mode can honestly say — and a file in neither shape, which still gets its JSON. The ones nothing was measured for are kept apart from the ones that were: unscored, duplicate and invalid all open onto *why*, and an invalid patch has no values to diff at all. Then the derived series, which are the numbers that can be plausibly wrong — best-so-far counts only *feasible* candidates and steps rather than slopes, an unscored candidate is absent from the chart rather than plotted at zero, the budget curve is cumulative while the per-iteration cost columns are not, each metric is charted in its own units, the line joining a metric breaks at a candidate it has no value for, and the trials recorded after the last iteration are named rather than folded into it. A run with two goals has no single best value, so it gets the **trade-off** between them instead of a pointer to somewhere else: both axes turned so better is up and to the right, which is the only way `Minimize(tokens)` reads correctly — the direction comes out of the objective expression, since nothing else in the record states it, and the geometry is asserted (which mark is above which) rather than that something was drawn. The staircase steps through the set the run itself called best — the front its end-phase report names, else the champion it picked when that front is empty, else what the last finished iteration had best so far — and says which of those it is, because they are claims of very different strength. The baseline is on the chart although no iteration ever reports it as a proposal, since it is what every other mark is read against; a candidate measured on only one of the two goals is named rather than quietly dropped; and with three goals or more the front of the pair on screen is computed for that pair and labelled as computed, because the recorded set is a front over more dimensions than a plane has. Also the page's shape: method, result, winner and candidates above the fold with every chart folded into drawers that are closed but already drawn, and the metric and unit pickers redrawing what they promise. And the line naming which experiment supplied the cases, which is a *guess* — a run record has nowhere to name its own experiment, so it is matched on the case ids in the split and reported as an overlap: a complete match is stated plainly, a partial one says how partial, two candidates go to the one accounting for more of the split, a tie goes by path so two scans agree, and nothing in common says nothing rather than naming the nearest file. Plus a log still being appended to, one with a corrupt line, a candidate the optimizer never labelled, a champion whose values the log never recorded, a run with no finished iteration at all, and a directory missing either half of the pair |
| `server.mjs` | served mode end to end: discovery over HTTP, saving back to disk, the mtime conflict guard, evaluator edits round-tripping, token enforcement, an optimizer log fetched over `/api/events` — including a candidate's trials, which are built from the `trial` events rather than the iteration summaries and so check the whole log came over the wire, and one trial's transcript, which is a second fetch for a path built out of the log and the only place a missing transcript can be told apart from a missing *file* |

`fixtures/optimizer-run` is synthetic, written by `fixtures/make_optimizer_run.py`. Nothing in the
library writes an `events.jsonl` yet — the optimizer's record layer still raises
`NotImplementedError` — so the page's reader is coded against the schema documented in
`optimization/record/events.py` and this fixture stands in for a real run until that lands.
