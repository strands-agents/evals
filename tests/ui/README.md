# Browser tests for `strands-evals ui`

The page served by `strands-evals ui` is a single HTML file at
`src/strands_evals/cli/assets/ui.html`. Its discovery, pairing and write logic lives in Python and
is covered by `tests/strands_evals/cli/test_ui.py`; what is left in the page is rendering, and
rendering is where it can be *confidently wrong* — claiming a trajectory is absent when it is
merely an unexpected shape, or counting a failure to judge as a skipped row. These suites run the
real file in jsdom and assert on what it puts on screen.

Not wired into CI, because CI has no Node toolchain. Run them by hand when the asset changes:

```bash
cd tests/ui
npm install          # jsdom only
npm test             # writes the fixture, then every suite
node standalone.mjs  # or one at a time
npm run fixture      # what `npm test` does first, for running a suite on its own
```

`server.mjs` starts the real `_ui_server` as a subprocess and forwards the page's `fetch` to it, so
it exercises the HTTP contract rather than a mock of it. It needs a Python that can import
`strands_evals`; override with `PYTHON=/path/to/venv/bin/python npm test`. Point the suites at a
different build of the page with `UI_HTML=path/to/ui.html`.

| Suite | Covers |
| --- | --- |
| `standalone.mjs` | the file opened with no server: bundled sample, folder picker, download-save, add/delete case, evaluator config editing, trajectories that are dicts or a `Session` |
| `fileorigin.mjs` | the file opened from disk over `file://`, which `standalone.mjs` does not cover — it boots at an http URL, so it never reaches the APIs an opaque origin restricts. `history.replaceState` refuses a URL it cannot verify against one, and that rejection used to abort rendering entirely |
| `extras.mjs` | the row cap, deep links — including one saved as `tab=optimization`, from when that section was a single view, which lands on the result it was looking at and is rewritten to the name the page now uses — reports missing their optional arrays, a mismatched experiment↔report pair, runs with only one half. Also the run list's two jump cells: the experiment and report columns open their own tab, but only where there is something behind them — a "not run yet" cell does what its row does rather than opening an empty Report — and a jump within the run already open must not re-read it from disk, since the unsaved-changes prompt only fires when the run *changes*. And the ink the property names are set in: jsdom does not substitute custom properties, so a computed `color` comes back as the literal `var(--inkN)` the stylesheet asked for, which is what field labels, column headers and detail keys are checked against — plus the muted ink itself against 4.5:1, so promoting the labels cannot just move the problem down to the hints. Then the metadata editor, where the contract is what reaches the file: a value is `Any`, so `4` has to land as a number and `hello world` as a string, a renamed key has to replace rather than join the old one, emptying the last key has to delete the whole dict, and a blank row the `+ key` button just offered is *not* an edit — mutating the case there would both mark it dirty for nothing and write a `""` key if saved before being filled in. The glyph strip and draft badge are read from the same objects, so an empty `{}` earning a glyph would be the same bug seen from the list. And the review pass, which is the only place in the page a bare keystroke changes the document: it moves the selection to the case being decided, `a` and `d` are off while a field has focus, `drop` is written out by Save like Delete rather than touching the file, and the pass closing is announced *after* the re-render that would otherwise clear the message. |
| `optimization.mjs` | the Optimization section, over `fixtures/optimizer-run`. The section itself first: it does not exist at all for a folder holding no run directory, so a folder of plain experiments reads as it did before there was an optimizer, and its tabs — **Runs**, **Setup**, **Overview**, **Progress**, **Candidates**, **Tunables** and, for a run with two goals or more, **Trade-off** — are this section's own rather than Evals' three renamed. That is one tab per question a tuning run is asked, which is the shape the optimization explorer on `poshinchen/evals` arrived at and the one this section took from it. It was a single Results tab with the search, the candidates, the knobs and the trade-off folded into drawers under the result, and a drawer is still the same page: five questions arrived stacked under the answer to a sixth. Links saved under the names that shape had — `tab=optimization` from when the section was one view, and `tab=opt-results` — both land on Overview, which is where the result they were looking at now is. Runs lists the run directories the way Evals lists experiment/report pairs, with the champion, the search, the stop reason and a marked row saying which run the other tabs are showing, so the list and the result cannot disagree. It also says what each run *achieved*, which is the question a list of runs is asked first and the one thing these rows did not answer — the objective's delta, coloured by the **interval** rather than by the gap, since a run whose interval straddles zero has shown nothing however large its gap and the list would otherwise promise what Overview then takes back; with the split named in the row, because held out against validation is the difference between a result and a hopeful one, and the interval itself on hover where it costs the row no width. A run still searching reads as not measured rather than as zero. Setup is the record as written and is read-only: it holds nothing to type into, because nothing in the page writes a `run.json`. It is in two halves, because the record is: the open list is the brief — the objective, the constraints and how much of the split has to meet them, the cases, the budget — and the machinery it was told to use, which is the surrogate, the selection rule, how a failed agent scored, where it ran and the run's own id, is a fold under it, since in one list those outnumbered the four lines a reader arrives for. Nothing is dropped, and nothing is said twice either: the goal metrics are a row only for an objective that does not state them — `Maximize(Correct)` with `Goal metrics: Correct` under it was the same fact twice — and the tunable blocks only where there is no space table to tag each key with them. It is also where the two spellings of that record meet — the fixture names the fields the way `optimization/record/events.py` documents them, while a `run.json` the optimizer really wrote puts the goal metrics in the `objective` roles of `metrics`, the tunable blocks inside `search.blocks`, the repeats in `runs_per_candidate`, the score model and pick rule under `name`, and say Pareto only in the objective string — so each of those rows is asserted against a config in the written shape, since a field read under one name is a row that is simply absent for every real run. **Tunables** is the knobs, which is one subject in two halves — what each was allowed to be, and what the fit beside the log says each one did. The first half is the **space**, which is the only account of the knobs that exist as against the ones some candidate happened to move: a key that was offered and never touched reads "0 of 10" rather than being absent, the denominator is the candidates and not the proposals, a text default is its length and not the digest recorded beside it, a key that only exists under one option says which, each key carries the `search.blocks` group that declares it, and a key the log changed that the space does not declare is warned about — while a record written before the field existed loses the table and gets the varied-keys line back, so the page is never silent about both. Setup is also where the **method** is, because no number on the tabs after it can be read without one: the search only saw train, the pick happened once on validation, and the experiment was never run itself — with the one line of it that every figure depends on, what was tuned and over how many cases of each split, repeated on Overview where those figures are. Then **Overview**, which is what a run row opens onto and what the result is — answer first: the card leads with the sentence, then the table it is read off, then the picture of the table, where it used to put a reader through a seven-column table and a chart before saying what either showed, and is headed by what it holds rather than by a qualifier, with the split it is on in ordinary case beside that label since a whole sentence set in small caps is how a heading is spelled and not how a sentence is read. The result itself is the champion against the baseline on the held-out split, where every figure has a wrong neighbour in the log it could have come from instead (the training best, the validation objective, a mean over the cases the search chose on). The verdict is the *interval*, not the gap, so there are logs differing only in that — one clearing zero, one straddling it, one negative, one with no interval at all, and one whose interval is narrow enough that rounding to two decimals would flip the verdict. Then the same comparison as a **picture**, which is what a reader who does not read the card still takes away — so it has to carry the same verdict: an interval clear of the line is drawn clear of it and one crossing it is drawn crossing, whatever the gap says, and the crossing case is the one kept at full strength rather than faded. It prints no figures, because the table above and the sentence below have them all and a third copy is the page saying one thing three ways; the numbers and the reading are on hover instead. Each bar is scaled to its own interval — a shared axis would have to put a 0.14 change in a score and a 150-token change on one, and the score would vanish — so the chart says that widths do not compare between rows, and names both the line and the sense of it, since a bar with an unlabelled axis is a score. Green and red come out of the objective expression and nowhere else: a rise in a `Minimize` metric is red where the same rise in a maximised one is green, and a metric the objective states no direction for — `tokens` as a constraint rather than a goal — is drawn in neither, since guessing from the name is how "+0.4 latency" comes out green. The objective gets its own always-up-is-better row, except on a single-goal run where its three numbers *are* the metric's and two identical bars would read as two findings. A zero-width interval — what two cases that agreed exactly report, and what any deterministic metric reports — is not drawn at all: scaled to its own row, a point lands hard against the margin, which reads as the furthest a result could go about a run that showed nothing of the kind. So a row needs width to be drawn, a report with none anywhere has no picture rather than an empty one, and the sentence stops calling a collapsed interval clear of zero and says instead that every case reported the same number — and anything the run was aiming at that ends up with no bar is *named* under the picture, because a reader who has just read two rows of the table and counts one bar is owed the reason rather than left to decide the drawing dropped it — with which of the two reasons it is, since a comparison that reported no interval at all and one every case agreed on are not the same fact, and calling the second "no interval" would contradict the `[-331, -331]` printed directly above it. The set it names is the same set the table leads with, so the two halves of the card cannot disagree about what the run was for. Which side of the line a bar falls on is the whole content of the picture and was the one thing it did not say, so each row ends in that reading as a word. In the table above it, a row prints every one of its figures to the decimals the widest of them needs: formatted a value at a time, a baseline of 0.1667 against a champion of exactly 1 came out `0.1667 → 1`, one quantity written two ways with the reader left to work out that `1` stands for 1.0000. The metrics a run was not aiming at are folded: a report carries every metric the evaluators produced, and on a run with one goal and one constraint the rest are what the champion happened to also do — rows of `+0` and a four-decimal `-0.0004` around the two that were the point. They are kept, because an unchanged cost is a finding, and a report the config names no metric of is shown whole rather than as an empty table with the answer in a fold under it. A `picked`-only run is labelled validation rather than held out, and reads `measured` where a test report says `means`, and the picture of it is faded to match that label rather than presenting the same shape with the same confidence. Then the **champion configuration**, which is what the card holds and so what it is headed by — "Winner" was a third word for one thing on a screen whose stats row and table column both said champion, and it named the candidate rather than the configuration behind it. It carries its lineage back to the baseline, only the settings that actually differ, a multi-line prompt diffed as a block, and what the copy button really hands over (the whole configuration, inherited settings included) — with the fallback saying so when the clipboard is unreachable. Then **Candidates**, which the tab treats as what `RunDirectory.reports()` says they are — an evaluation run of one configuration. So a row opens onto the diff against the *baseline* (not the parent, which `changed_keys` already is), its measured metrics and every trial grouped by split in run order; the search reaches into the configuration values, so a phrase from a tuned prompt finds the candidate that says it; and "open as report" builds an `EvaluationReport` from the trials and hands it to Evals' Report panel, where a failed trial still counts as a failing row, a case input the trial never recorded is named as absent rather than printed as `undefined`, and the `{hash, format}` transcript pointer is left out rather than dressed up as a recorded conversation. That panel is *borrowed*, not reassigned: the jump says whose report is in it and gives the one click back, because overwriting the report Evals had loaded while its Runs tab went on highlighting that run was the page contradicting itself. A trial row opens further, onto the one thing on this tab that is not derived from the log: how it ended, what each evaluator made of it, what it cost, the answer it gave, and the **conversation** behind it — a file in the run directory that the log only points at by hash. So the transcript is read off the *document* rather than the `format` the pointer claims, in both shapes: a `Session`, counted in spans and labelled by span kind, since printing a tool's result as a message would have the model saying it out loud; and a list of Strands messages, counted in messages, with usage on the one that recorded any and reasoning shown but set apart from what the model actually said. Tool output arrives as a JSON string far more often than as a structure, so a lone `{"output": "..."}` is laid out as the tool's text rather than as the envelope it came in. And the four ways there can be nothing to show are four different facts about a run, so they read as four: a trial that recorded no transcript, a pointer whose file the opened folder did not hold (named, with the picker's depth limit as the likely reason), a pointer the server answers 404 for — "not in the run directory", which only served mode can honestly say — and a file in neither shape, which still gets its JSON. The ones nothing was measured for are kept apart from the ones that were: unscored, duplicate and invalid all open onto *why*, and an invalid patch has no values to diff at all. Then **Progress**, whose derived series are the numbers that can be plausibly wrong — best-so-far counts only *feasible* candidates and steps rather than slopes, an unscored candidate is absent from the chart rather than plotted at zero, the budget curve is cumulative while the per-iteration cost columns are not, each metric is charted in its own units, the line joining a metric breaks at a candidate it has no value for, and the trials recorded after the last iteration are named rather than folded into it. Every one of those series is read off an axis, so the axes are asserted too: the ticks fall on round steps with the domain widened out to them, since five ticks interpolated across the data gave 0.4975, 0.5612, 0.6249 — the extremes of the run and four numbers nobody chose — and each axis says which way its own metric wants to go rather than carrying a bare metric name, which on a minimised one had the label and the direction of the drawing contradicting each other. A chart whose x axis is a *list* names the candidates under their own slots with the iterations grouped in a row below and a divider where the search turned over: labelled "it 0" … "it 5" at the boundaries it named the groups and left every mark anonymous, so a reader looking at the best point had no way to find it in the Candidates table. A candidate id too wide for its slot gives way to the proposal number that table shows beside the id — but only where that is actually narrower, since `#10` for `c10` renames a candidate for nothing — and labels that still do not fit are thinned by their own width rather than overlapped. A run with two goals has no single best value, so it gets a **Trade-off** tab instead of a pointer to somewhere else — and a single-goal run does not get the tab at all, though a link naming it still lands somewhere that says why rather than on a heading over nothing: both axes turned so better is up and to the right, which is the only way `Minimize(tokens)` reads correctly — the direction comes out of the objective expression, since nothing else in the record states it, and the geometry is asserted (which mark is above which) rather than that something was drawn. The staircase steps through the set the run itself called best — the front its end-phase report names, else the champion it picked when that front is empty, else what the last finished iteration had best so far — and says which of those it is, because they are claims of very different strength. The baseline is on the chart although no iteration ever reports it as a proposal, since it is what every other mark is read against; a candidate measured on only one of the two goals is named rather than quietly dropped; and with three goals or more the front of the pair on screen is computed for that pair and labelled as computed, because the recorded set is a front over more dimensions than a plane has. The other half of Tunables is the **effects** drawer, which is the one estimate in the section — fitted into `effects.json` after the fact, and the only place that says a *key* did something rather than that a candidate did, which is why it is beside the space rather than under the result. So an interval crossing zero is drawn faint, because the run does not settle it; `p_positive` is the chance the metric rose, which for `Minimize(tokens)` is flipped into the chance it got worse (unflipped, a confident +180 tokens would have read as 0.99 likely better); the bar still points the way the number went while the column carries the verdict; the keys the model left out are named with why, so a key absent from the plot is not read as a key that did nothing; and a fit that failed its own held-out check says so in its words. Since nothing in the library fits one, most runs have none and the drawer is simply absent — including for a model that was attempted and came back empty, which for a reader is the same thing. The stop reason is the reason and not the message beside it, which a real record writes for whoever set the budget and which, nested in parentheses after the word it restates, was the longest line on the tab; it is on hover instead. Also the section's shape: Overview carries the result and the winner with nothing folded over them, every tab is rendered whether or not it is the one on screen, what is still a drawer starts closed but already drawn, and the series and unit pickers redraw what they promise. One chart answers "by candidate" for both the objective and every metric, because they are the same picture in the same units-per-series and the objective panel was the metric panel with its picker taken off — so the picker is asserted to offer the objective first and to carry its legend only while the objective is what is drawn, a metric chart having no best-so-far line to name. Spend and trial outcomes share the one drawer left on Overview, whose fold states both halves, since two folds made one question — what did this cost — read as two topics with the trial count in one and the spend it counts in the other, while the rollouts those trials spent are charted on Progress against the budget, which is where the question is whether the run stopped because it was done or because it ran out; and the best training objective is a stat in the row over the charts rather than a hero number beside the result, where a bare best-ever value read as a second, bolder answer to the question the interval above it had already answered more carefully. Within that row it comes *last*, after the champion and the spend, and names the candidate it belongs to: it is a figure from inside the search, and on a run where the training high went to a candidate validation did not pick, leading with it had the first stat and the second naming two different candidates with nothing saying how that happens — so the note says it was not the pick, and the whole of why is on hover. The token total is not a stat there at all, because the fold of the drawer that charts it already reads "277k tokens · 82 trials". And the line naming which experiment supplied the cases, which is a *guess* — a run record has nowhere to name its own experiment, so it is matched on the case ids in the split and reported as an overlap: a complete match is stated plainly, a partial one says how partial, two candidates go to the one accounting for more of the split, a tie goes by path so two scans agree, and nothing in common says nothing rather than naming the nearest file. Plus a log still being appended to, one with a corrupt line, a candidate the optimizer never labelled, a champion whose values the log never recorded, a run with no finished iteration at all, and a directory missing either half of the pair |
| `server.mjs` | served mode end to end: discovery over HTTP, saving back to disk, the mtime conflict guard, evaluator edits round-tripping, token enforcement, an optimizer log fetched over `/api/events` — including a candidate's trials, which are built from the `trial` events rather than the iteration summaries and so check the whole log came over the wire, and one trial's transcript, which is a second fetch for a path built out of the log and the only place a missing transcript can be told apart from a missing *file*, and the effects model, which is a third. Also that the files a run owns — its transcripts, its effects model, its champion's values — are not reported back as files the scan could not use, and that the result in the runs list is read out of the end phase by the *server*: the page has not fetched that log yet when the list is drawn, so a result computed only in the page would be blank over HTTP while the same folder opened from disk filled it in |

`fixtures/optimizer-run` is synthetic and **not committed** — `fixtures/make_optimizer_run.py`
writes it, and `npm test` runs that first. It is 84 files, 80 of them recorded conversations named
by content hash, which checked in meant every review of this directory was mostly generated JSON.
The generator is deterministic, so the fixture the assertions were written against is the one you
get.

On this branch nothing in the library writes an `events.jsonl` — the optimizer's record layer
still raises `NotImplementedError` — so the page's reader is coded against the schema documented
in `optimization/record/events.py` and this fixture stands in for a real run until that lands.
`workstream/optimizer-workflow` does write one, and the page has been run over a directory it
produced. Two assertions come directly out of that: the split, which a real record writes as the
*fractions* at `split.train` with the case names under `split.cases.train` rather than the names
at `split.train`; and a run's own `result.json`, which is covered on the Python side because it is
the scan that has to know not to read it as an experiment.
